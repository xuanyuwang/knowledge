Contract and workflow

For an authorized request [S,E), eligible conversations must remain governed by the existing population and request filters. Feature lookup must return qualifying use only for those conversation/agent pairs. Scan bounds must control physical work without silently redefining eligibility or discarding supported evidence. This investigation does not change product code, feature predicates, ticket status, deployment or production data.

Findings and worked scenarios
These are demonstrated mechanisms and conditional results. Customer prevalence and production performance remain unmeasured. Existing semantics are separated from the new endpoint’s scan issue.
T1 · Confirmed scan behavior; production cost unknown
Seven new evidence families scan historical data before eligibility intersection
Trigger: One-day request, one eligible conversation/agent, months of feature history for the same agent.
Trace: The evidence constructor supplies only an agent predicate. Feature rows are reduced to pairs before the ordinary join with assistance_usage_population. The final join excludes other conversations from the answer but cannot be assumed to prune all preceding work.
Observed: A single-node synthetic MergeTree with 180,000 history rows returned the identical eligible pair with unbounded read_rows=180,002 and exact request bounds=2,050. Counts include the two tiny lookup tables.
Impact / limit: More history can increase source reads, pair reduction, memory and transfer even for a short request. This is demonstrated locally, not a measured production regression.
Fix boundary: Apply the requested [S,E) interval consistently to every physical evidence source, following the existing assistance APIs, and retain the final eligible-pair intersection. Audit copied timestamps and internal matching separately from source-scan alignment.
Regression: Seed selected-agent history far outside the request, in-range evidence, out-of-cohort pairs and skewed copied timestamps. Assert exact results and inspect each physical read/remote plan; benchmark representative deployed data.
T2 · Verified existing time-semantics difference; prevalence unknown
Copied timestamps can disagree under the same requested interval
Trigger: Conversation start changes after an evidence row copied the earlier value, or independent projections are refreshed at different times.
Trace: Events and Conversations writers copy the conversation start field, independently of event creation/ingestion time. The upsert-message path can move StartedAt earlier based on a message timestamp. No maximum correction delta is enforced in that inspected loop.
Observed: Synthetic evidence with copied start outside [S,E) is excluded by existing APIs but retained by the current new pair-based lookup when its cohort pair is supplied. Late arrival with an unchanged in-range copied start remains included in both.
Impact / limit: Late arrival and copied-time disagreement are different states. Applying the same request interval aligns source bounds but does not make independently copied timestamps agree. The current unbounded new lookup and existing bounded APIs can therefore return different evidence.
Fix boundary: Use the existing requested-range behavior as the scan baseline. Document and investigate timestamp-copy, correction and reindex behavior as a separate correctness question; no fixed-day expansion is proposed.
Regression: Test copied timestamps before/inside/at the end of the request, unchanged copied time with late creation, and a conversation moved into/out of the request. Keep synthetic cases distinct from observed production data.
T3 · Reproduced on main reader and PR reader; inherited behavior
Summary still loses use on an internal exact timestamp join
Trigger: Generation action at copied start October 1 00:00 and a qualifying copy at October 1 01:00, with the same conversation/agent. Both timestamps are inside the request.
Trace: The feature joins valid generation to use USING (conversation_id, conversation_start_time, agent_user_id), before the new API can apply its pair intersection.
Observed: Legacy used_summarization_count=0; new Summary evidence returns no pair. Generation count remains 1. Expanding source ranges cannot make unequal join keys equal.
Impact / limit: A conversation can lose Summary-use credit despite having both qualifying records. Aligning source bounds cannot resolve unequal internal join keys.
Fix boundary: Choose whether timestamp equality is an intended feature contract. If it is removed, preserve conversation/agent identity and decide whether generation-to-copy linkage needs a stronger annotation/session key. Keep any legacy behavior correction separate from a scan-only change.
Regression: Same pair, differing copied times inside or outside the interval; unrelated generation/copy; wrong agent and duplicate generations.
T4 · Reproduced on main and PR legacy readers; new evidence lookup differs
Time-bucket anchors can hide usage even when both source scans cover it
Trigger: Two-day request. Conversation/message copy is October 1; usage annotation or generation/copy pair is October 2; no message/conversation aggregate exists for that agent on October 2.
Trace: GenAI left-joins usage aggregates to message aggregates by agent/time bucket. Summary left-joins summary aggregates to conversation aggregates. Neither join proves conversation identity across those buckets.
Observed: Legacy daily GenAI use is 0 and Summary use is 0, even with a two-day source interval that contains all rows. The new GenAI and Summary evidence queries return the eligible pair; new output buckets use population time. Notes/Workflow instead emit their event-copy day.
Impact / limit: Identical source scan ranges do not guarantee matching totals or trend placement. The legacy combined assistance API has the same message-bucket anchoring pattern.
Fix boundary: State whether the product groups adoption by population conversation start or feature-source copy. For conversation adoption, carry the pair plus chosen population time through aggregation; do not borrow legacy aggregate totals as the numerator.
Regression: Same pair copied across midnight; UTC and non-UTC day/week boundaries; missing anchor bucket; include/exclude metadata; Agent and Team totals.
T5 · Reproduced existing dependency and cross-API parity gap
Notes and Workflow depend on cluster choice and a second conversation copy
Trigger: Conversations contains the eligible conversation and matching typed evidence. Events has the JSON usage event but lacks its conversation row; matching metadata is also available.
Trace: Without metadata, legacy Notes/Workflow read Events and inner-join events to Events conversation_d by conversation ID. With metadata, legacy switches to Conversations. New Notes/Workflow always use the Events branch, even when the cohort was filtered with metadata in Conversations.
Observed: Legacy no-metadata and new evidence queries return no Notes/Workflow usage. Adding a matching metadata filter causes both legacy endpoints to return 1 via Conversations.
Impact / limit: The same date range can cover different stored histories and return different usage merely because the selected source changes. Padding timestamps cannot restore a missing Events conversation row.
Fix boundary: Verify historical coverage, ingestion/retention/reindex behavior for both projections. Decide whether the new endpoint should require a second Events conversation record after cohort eligibility is already established. If removing that join, review source/agent/metadata gates explicitly.
Regression: One cluster missing conversation or event; copied times disagree; matching metadata changes source; wrong-agent conversation rows; typed versus JSON payloads.
T6 · Reproduced inherited population behavior; not a new evidence-query bug
The eligible population still filters copies before selecting the latest version
Trigger: An older conversation row starts October 1; a newer row for the same pair starts October 3; request is October 1. An in-range message copy remains.
Trace: The population applies exact time bounds in the conversation source WHERE, then ORDER BY update_time DESC LIMIT 1 BY pair. The newer out-of-range row is removed before version selection. Message copies are also independently range-filtered.
Observed: The population still returns the October 1 pair. A separate missing-message probe returns no population despite feature evidence.
Impact / limit: Calling this cohort globally current would overstate its contract. Widening only feature scans cannot recover a pair excluded by a stale message copy or correct an old version retained by prefiltering.
Fix boundary: Keep this separate from CONVI-7777 scan-only changes unless latest-state semantics are explicitly required. Define bounded candidate discovery versus global latest-state selection and preserve frozen ConversationStats behavior until reviewed.
Regression: Newest version moves outside/inside the range; message and conversation disagree; same pair with multiple versions; new agent assignment; labels ON/OFF paths.
T7 · Reproduced shared boundary behavior
Whole-second SQL formatting changes fractional request boundaries
Trigger: Requested interval is [October 1 00:00:00.500, 00:00:01.500).
Trace: The common timestampFormat is 2006-01-02 15:04:05. Both request endpoints are formatted without fractions before source conditions are built.
Observed: A KB event at 00:00:00.250 is included although it precedes the request; one at 00:00:01.250 is excluded although it is inside. The query uses [00:00:00,00:00:01).
Impact / limit: Exact DateTime64 membership at API boundaries is not preserved. Normal whole-day UI requests do not trigger this specific case; direct fractional requests can.
Fix boundary: Use typed timestamp arguments or a format retaining required precision consistently across source and metadata filters. Do not fold this shared behavior correction into an unreviewed window change.
Regression: Fractional lower/upper endpoints, zero-width ranges, microsecond-before/at end, and equivalent metadata-filter requests.
T8 · Smart Compose source-observed; adherence metadata gap reproduced
Adjacent APIs have different attribution and filter contracts
Trigger: A Smart Compose insert occurs in a later hour than conversation start, or an adherence request contains nonmatching metadata.
Trace: Smart Compose filters analytics_event.event_time and joins to agent/hour of conversation starts. RetrieveAdherences discards the parsed metadata inclusion/exclusion lists.
Observed: All inspected scans remain time-bounded. Smart Compose attribution cannot be equated to conversation-level membership from these joins. The adherence fixture survives a nonmatching metadata filter with the same response as no filter.
Impact / limit: A uniform historical scan range cannot make event-time metrics, conversation-start metrics and metadata semantics equivalent. Silence/Hold or P2 features need explicit contracts before admission into the new union.
Fix boundary: Keep Smart Compose and email additions outside V1 as scoped. When revisiting them, require conversation-linked actual-use evidence and explicit filters. Define whether adherence metadata should be honored or rejected, then address that API separately.
Regression: Long conversation with later-hour insert; another conversation in that hour; same text twice; nonmatching metadata for adherence; missing delivered-action linkage.


Inspect the captured SQL results
Direct SQL probes isolate query semantics. New evidence probes use a manually supplied eligible-pair table; they are not full RPC calls. Population probes execute the actual population query separately. An empty evidence result does not necessarily make the combined metric zero if another feature qualifies.


What CONVI-7777 should validate
  1. Agree on four distinct contracts: exact eligible conversation range; evidence source scan range; chosen output bucket time; and historical availability/retention by source. The same request should use a consistent scan policy across all participating feature sources, with justified exceptions for different clocks. A common scan span is not itself proof of equal results.
  2. Use the requested [S,E) interval for evidence source scans, matching existing assistance APIs, and keep the population interval unchanged. Apply bounds to annotations, events, required conversation copies, and supporting metadata reads where applicable. An eligible-agent predicate or final cohort join is not a substitute for physical source bounds.
  3. Investigate copied timestamp disagreement, ingestion/reindex behavior, retention and missing-copy prevalence separately. These checks explain cross-API completeness differences; they do not introduce an additional fixed-day scan window.
  4. Keep a semantic matrix for every family: aligned time; late arrival with unchanged copy; copied-time disagreement before/inside/after the interval; exact boundaries; generation/use disagreement; population/message disagreement; cross-day/week buckets; metadata include/exclude/both; missing cluster copy; wrong agent; duplicates; source/bot/dev-user gates; and Agent/Team/overall attribution. Validate rare cases that feature-internal joins can still drop.
  5. Validate source bounds in generated SQL and actual physical/remote plans. On deployed ClickHouse/version/data, record read_rows, read_bytes, memory, result identity and network/remote work for representative 1-day, 7-day and 30-day requests, narrow and broad agent audiences, and concurrent calls. Do not treat fewer returned pairs or green semantic tests as production performance proof.
  6. Preserve legacy RPCs in the scan-only change. T2–T8 are inherited semantics or separate parity decisions; migrate/fix them only with explicit scope and independent regression evidence. Add the findings to follow-up tracking without claiming that separate Linear tickets or owners already exist.


Effects beyond the diff
The same request reaches two independently populated clusters, different copied clocks, metadata materialized views and multiple feature-internal joins. The new endpoint cannot repair evidence already removed by its message-anchored population. Main and PR GenAI/Summary readers were compiled separately and their focused results agree. Other inspected legacy source readers are identical at these revisions.
Known related issues remain in the existing issue register: metadata exclusions under non-nullable joins, Summary payload semantics, Notes metadata projection enums, attribution and denominator contracts. The Notes metadata fixture deliberately supplies the query’s expected type 5 to isolate source dependency; it does not prove production enum parity.


Non-blocking maintainability
Use separate names for exact eligibility and evidence scan bounds. Centralize an adopted policy and document source clocks and cluster switches. These suggestions do not replace the semantic decisions or measurements.


Recommendation
Use the requested [S,E) interval, matching existing assistance APIs.
Apply those bounds to every participating evidence source, preserve exact eligibility, and validate physical scans plus feature-internal joins. Resolve inherited correctness differences as explicit follow-ups. The current new API is cohort-filtered but has no bounded evidence-scan contract; existing APIs are bounded but are not semantically interchangeable.

Pinned sources
  1. Shared interval bounds — The default source interval is start-inclusive and end-exclusive. The formatter at line 37 keeps whole seconds.
  2. All seven new evidence queries — Only eligible agents are applied inside feature sources; eligible pairs are joined after feature reduction. No source timestamp bounds are supplied.
  3. Notes cluster switch — Metadata requests switch from Events to Conversations, including a different payload projection.
  4. Workflow cluster switch — Metadata requests switch from Events to Conversations.
  5. Summary exact timestamp join — Generation and use must agree on conversation, agent and copied start time. This is preserved from main.
  6. GenAI aggregate joins — Usage joins message aggregates by requested grouping keys, including time buckets when requested.
  7. Population source and version selection — Both message and conversation copies receive exact bounds. Conversation time filtering occurs before latest-row selection at lines 79-94.
  8. Smart Compose hour matching — Actual event time is filtered; attribution uses agent/hour instead of a conversation ID.
  9. Adherence metadata discarded — The reader discards parsed include/exclude metadata lists. Source timestamps still have bounds.
  10. Earlier messages can change start time — The inspected loop moves start time to an earlier message timestamp without a local maximum-delta guard.
  11. Events copy conversation start — ConversationStartTime comes from the supplied conversation, while CreateTime is ingestion wall clock.
  12. Conversations projection copies start — Annotations and events copy conversation.StartedAt; their own creation time is a different column.
  13. Legacy combined API — Message, moment and event scans receive time bounds; results are anchored on message aggregates.
  14. Conversation source sort key — Base source tables are time-led. Do not assume every base table has monthly partitions; several by-conversation/metadata views do.
  15. Events source sort key — Events source keys begin with copied conversation start time; analytics_event uses event_time instead.
