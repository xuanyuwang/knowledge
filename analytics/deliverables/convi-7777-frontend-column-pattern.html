The contract for this column

Input → expected result

A user opens Assistance Used or changes its filters. The Agent and Team leaderboards receive the same selected date range, attributes and role options as the page’s other metrics.

Each eligible row shows the percentage of its eligible conversations with at least one qualifying assistance use. “Use” follows the dedicated API’s definition; merely offering assistance does not establish use.

Boundaries that matter

Count a conversation once per agent even if several assistance features were used. A Team result sums its member-agent counts. Always use the numerator and denominator from the same grouped API result.

Preserve measured zero. Show unavailable data as N/A. Keep the existing metrics working when this request fails. Trend charts, backend implementation and rollout are outside this frontend change.

Worked example: why insertion order matters
An eligible agent has 0 assisted conversations out of 8 and no rows in the existing assistance-use results. ConversationStats still has 10 conversations, 2 conversations/day and AHT 120s; AgentStats has 5 active days. These fixtures deliberately keep the dedicated API denominator separate from ConversationStats.
  1. Broken teaching state: enrichment asks the helper for a row. With no map entry, it creates a temporary object. The loops set volume/AHT/active days but do not insert that object.
  2. Usage insertion runs later, creates a fresh object, stores 0%, and loses the old metrics. Its powered-by-AA denominator is also absent.
  3. Reviewed final state: usage inserts the map entry first. Every enrichment loop gets that same object and preserves all existing metrics.
This normal path arises for eligible agents/teams with no other assistance activity. The hook regression test covers both tables. No outstanding bug is claimed for the corrected code.

Effects beyond the changed lines
Shared table behavior
The numeric accessor inherits useCustomSorting. Existing column config persists hidden IDs separately for Agent and Team. The eligibility set’s historical “alwaysVisible” name does not force a user to show the column.
New row population
This API can introduce rows absent from older assistance results. Row creation changes which entities the table can show, so preserving enrichment is part of the feature’s correctness.
API compatibility
The pinned web client (2.30.77 at implementation) lacks this RPC. The typed transport bridge uses the normal request wrapper. A population-only response yields no grouped data; a grouped zero numerator is interpreted as measured zero under the final API contract.
Rollout invariant: a server that returns grouped denominators must also compute assistance-use counts. Proto3 omission of a zero numerator cannot distinguish “computed zero” from “not implemented.” No deployed-server state is asserted by this frontend review. Current knowledge records backend count implementation separately.

A checklist for the next column
  1. Write its meaning, denominator, numeric unit and zero/N/A behavior.
  2. Find whether existing data already carries it; add or adjust a query only if needed.
  3. Thread the result to the relevant Agent/Team hook and join using a stable resource name.
  4. If the query can introduce rows, insert them before other metric enrichment.
  5. Use the same property key for row type, accessor, eligibility and CSV header.
  6. Format at the cell; keep sorting and CSV values numeric. Reuse user visibility and export filtering.
  7. Extract labels and verify real zero, missing data, new rows and both table exports.
