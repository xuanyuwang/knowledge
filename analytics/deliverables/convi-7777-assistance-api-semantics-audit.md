# CONVI-7777 — V1 assistance API semantics and alignment audit

**Date:** 2026-10-09. **Status:** Source-level investigation; no production data or deployment validation. **Source checkpoints:** go-servers `origin/main` `48d308822e90e17d2ca190987220601601ee9d97`; Director `origin/main` `da2e210926b60faefcdef8ede940ff40575d0e50`; cresta-proto `origin/main` `40941b12b272b98c6000b4d528b77e4150fa9f55`. Local main checkouts are older; line references below refer to these fetched revisions.

## The contract to preserve

The [proposed feature inventory](convi-7777-pm-feature-inventory.md) has 10 v1 categories. This audit covers their seven existing assistance stats RPCs, plus `RetrieveConversationStats` for the page's total conversation count. Chat Smart Compose and all email assistance are P2 and are outside this V1 API comparison; their source evidence remains in the feature inventory. Silence/Hold is a conditional v1 candidate gated by `enableSilenceHoldHintsTab`, with its qualifying-use signal pending.

**Alignment decision (October 12):** Align the **conversation population** used for the new percentage. Treat each existing feature RPC's SQL and code as the source of truth for its current per-feature count and use predicate. The new numerator is a distinct-conversation union of those qualifying feature signals within one eligible cohort; its denominator is that same cohort. Existing response totals cannot be added to produce this percentage because they count actions, events, sessions, or different conversation populations. Do not silently redefine the current per-feature counts while building the new API. Where current SQL conflicts with proposed product wording or appears defective, record the discrepancy and decide whether to change the existing RPC separately before claiming parity.

## Filters and grouping shared by these RPCs

- All handlers resolve requested users/groups through `ParseUserFilterForAnalytics`, including ACL, group membership mode, `filter_to_agents_only`, and optional deactivated-user exclusion. With GROUP grouping, most RPCs query per agent, then add agent results to each selected group. A conversation handled by two agents can therefore be counted twice in a team sum. Overlapping groups can each receive it. [resolver](https://github.com/cresta/go-servers/blob/48d308822e90e17d2ca190987220601601ee9d97/insights-server/internal/analyticsimpl/common_user_filter.go#L127-L190); [example group aggregation](https://github.com/cresta/go-servers/blob/48d308822e90e17d2ca190987220601601ee9d97/insights-server/internal/analyticsimpl/retrieve_suggestion_stats.go#L163-L241).
- `parseClickhouseFilter` applies a required half-open time range (`>= start`, `< end`) to each target table. For these V1 assistance RPCs it defaults to **conversation start time**. It also lowers user, behavior, policy, moment, use case, language, duration, hint type, voicemail exclusion, and metadata-moment filters. Unsupported table columns are not handled uniformly: behavior/policy/moment may become `false`, while use case/duration may become `true`. This can make a feature count disappear or silently ignore part of a filter depending on its source table. [parser](https://github.com/cresta/go-servers/blob/48d308822e90e17d2ca190987220601601ee9d97/insights-server/internal/analyticsimpl/common_clickhouse.go#L320-L666); [column mapping](https://github.com/cresta/go-servers/blob/48d308822e90e17d2ca190987220601601ee9d97/insights-server/internal/analyticsimpl/common_clickhouse.go#L1900-L1947).
- **October 13 frontend check:** The Assistance Insights chart and Assistance Used leaderboard do not set `conversationTimeRangeField`. The shared request hook forwards it only when supplied in `filterOptions`; ConversationStats defaults the unspecified value to `conversation_start_time`, selecting end time only for an explicit ended-at request. Thus the current page's total conversation count uses conversation start time, matching the audited V1 feature requests. This is a page-specific finding, not a claim about every ConversationStats caller. [chart request](/Users/xuanyu.wang/repos/director-convi-7777-assistance-usage/packages/director-app/src/components/insights/assistance/assistance-insights-container/AssistanceInsightsContainer.tsx) [leaderboard request](/Users/xuanyu.wang/repos/director-convi-7777-assistance-usage/packages/director-app/src/components/insights/assistance/assistance-insights-statistics/assistance-used-page/AssistanceUsedLeaderboardContainer.tsx) [request hook](/Users/xuanyu.wang/repos/director-convi-7777-assistance-usage/packages/director-app/src/components/insights/hooks/util-hooks/useInsightsRequestParams.ts) [backend default](/Users/xuanyu.wang/repos/go-servers-convi-7777-assistance-usage/insights-server/internal/analyticsimpl/common_clickhouse.go)
- These RPCs construct included/excluded metadata-moment joins. The shared parser currently rejects a metadata **value-or-missing** combination when included and excluded identities overlap; this is tracked separately in CONVI-7708. Notes and Guided Workflow additionally switch physical clusters when metadata is requested. The new API must define its own supported filter set rather than claiming parity from a shared parser call alone. [parser guard](https://github.com/cresta/go-servers/blob/48d308822e90e17d2ca190987220601601ee9d97/insights-server/internal/analyticsimpl/common_clickhouse.go#L667-L694).
- All feature RPCs support agent/time grouping in their ClickHouse queries. HintStats additionally supports behavior/policy; GuidedWorkflowStats supports workflow. GROUP is implemented in Go through per-agent results. The existing Director leaderboard requests daily Agent+Team and Group results, but the proposed period percentage must be calculated from period-level distinct conversation keys, not an average of daily rates. [Director request](https://github.com/cresta/director/blob/da2e210926b60faefcdef8ede940ff40575d0e50/packages/director-app/src/components/insights/assistance/assistance-insights-statistics/assistance-used-page/AssistanceUsedLeaderboardContainer.tsx#L30-L95).

## Alignment findings and required action

1. **Define one cohort before feature union.** Recommend the existing Assistance leaderboard's `RetrieveConversationStats` population as the initial compatibility target: same time basis, source/bot setting, dev-user exclusion, agent eligibility, ACL, use case, duration, voicemail and metadata filters. Decide explicitly whether zero-message conversations should be included; the current total excludes them. Root numerator and denominator in the same eligible conversation/agent keys, then join feature evidence to those keys. This aligns population without changing current per-feature counts.
2. **Preserve each feature's current use semantics.** Use the predicates in its existing SQL and code to identify qualifying feature evidence, then deduplicate eligible conversation/agent keys for the new numerator. Keep the existing action, event, or session count unchanged. V1 feature signals are hint positive action/doc-chip, GenAI used moment, Summary's current valid-summary/use-event rule, Notes copy, KB search, workflow document use, and three chat Suggestions. Chat Smart Compose and all email assistance are P2. Gate any Silence/Hold branch on `enableSilenceHoldHintsTab` and settle its qualifying-use signal before counting it. Feature-level parity checks should compare matching predicates and filters; aggregate event/session counts cannot directly validate a distinct-conversation numerator.
3. **Resolve two metadata-path defects before claiming parity for those paths.** NoteTakingStats uses event type 5 and GuidedWorkflowStats uses type 4 on the conversations cluster, while its DB enum types are 17 and 14. Generated SQL goldens confirm those exact predicates. This is a confirmed source-contract mismatch; live impact still needs a targeted test or data check. Correcting the new query alone would produce different results from the current metadata-filtered RPCs; align or explicitly exclude those paths from parity comparisons until the existing RPCs are corrected. [Conversations-cluster DB enum](https://github.com/cresta/cresta-proto/blob/40941b12b272b98c6000b4d528b77e4150fa9f55/cresta/nonpublic/event/event.proto#L70-L115); [events-cluster enum](https://github.com/cresta/cresta-proto/blob/40941b12b272b98c6000b4d528b77e4150fa9f55/cresta/nonpublic/clickhouse/events/event_enums.proto#L1-L27).
4. **Do not use HintStats sent totals as a correctness oracle.** Its SQL unions behavioral and nonbehavioral sent aggregates, then takes `MAX` rather than their sum. For a group with both categories, the reported sent total can omit one category; the generated golden SQL has the same structure. This does not change the new metric's distinct followed-conversation rule, but deserves separate validation if the existing page metric is used for comparison. [query](https://github.com/cresta/go-servers/blob/48d308822e90e17d2ca190987220601601ee9d97/insights-server/internal/analyticsimpl/retrieve_hint_stats_clickhouse.go#L301-L364).
5. **Resolve the Summary wording mismatch explicitly.** `RetrieveSummarizationStats` uses `summarization_payload_data_type IN (1,2)` on the conversations cluster, but the PostgreSQL event oneof and the indexer map 1=copy all, 2=edit note, 3=copy note. The existing count therefore includes edits and misses single-note copies, while the proposed V1 inventory says “copy only.” For parity, the new API would use the current 1/2 predicate. If PM intends copy only, correct the existing RPC to 1/3 as a separate, deliberate semantics change and validate its impact before using it as the new API's source of truth.

**Answer to “clean up first?”** Align the new API's conversation cohort and attribution first, while preserving the existing per-feature count semantics. A broad rewrite of those RPCs is not a prerequisite. The Notes/Guided Workflow metadata mismatch and Summary wording conflict need explicit resolution before parity can be claimed for those cases. HintStats sent aggregation needs a separate follow-up; its sent count is not a conversation-use count. This conclusion is source-level and does not assert deployed behavior.
