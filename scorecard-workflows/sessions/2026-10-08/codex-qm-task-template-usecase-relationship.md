# QM task, template, and use-case relationship

- Date: 2026-10-08
- Primary source repo: `/Users/xuanyu.wang/repos/go-servers`
- Source context: main checkout `435cb9047a`; refreshed `origin/main` to `975adf2eb3` and verified the relevant task/template paths have not changed. Related Director main checkout `f47845f4f7`, `origin/main` `a0952b6862`; cresta-proto main checkout `a52824040e`, `origin/main` `d7d35365dc`.
- Question: Should a QM task inherit use cases from its scorecard template, and what relationship must be enforced?

## Current contract

1. A scorecard template has repeated `usecase_names` in the public proto (`cresta-proto/cresta/v1/coaching/scorecard_template.proto:77-79`) and `usecase_ids` on each stored template revision. An empty or NULL stored array is currently treated as all use cases by template lookup (`go-servers/shared/qa/scorecard_template.go:104-135`).
2. The supported QM task setup flow uses `QMTaskContentConfig.scorecard_template_name`, but the public `DirectorTask` has **singular** `usecase_name` (`cresta-proto/cresta/v1/coaching/task.proto:52-54,129-135`). `director.tasks` likewise has singular nullable `usecase_id` (`go-servers/apiserver/sql-schema/gen/model/tasks.go:69-82`). It has no stored `usecase_ids` array today. Multiple QM tasks may reference a template; task identity also carries audience, schedule, quota, and conversation filters.
3. Director's QM task form writes `scorecardTemplate.usecaseNames[0]` (`director/packages/director-app/src/components/qa/qa-task-setting-modal/hooks/useUpdateDirectorTaskConfig.ts:185-205`). Create converts and persists that payload without loading the template to check scope (`go-servers/apiserver/internal/coaching/action_create_director_task.go:46-64`). Update converts the payload, then copies the task configs while leaving the existing use-case column unchanged (`action_update_director_task.go:47-95`). Thus the task field is a copied singleton; neither inheritance nor consistency is enforced by the backend.
4. The copied field is **used as a task-query filter**. `ListDirectorTasks` matches request use cases against `tasks.usecase_id` (`action_list_director_task.go:256-281`); Task Home and QM Report both send the current use case (`director/packages/director-app/src/components/qa/hooks/qa-task-home-filter/useQATaskHomeFilters.tsx:233-241`, `.../qa/report/tabs/QAReportTabs.tsx:45-64`). `RetrieveQMTaskStats` filters templates by requested use cases, then tasks by singular `usecase_id` (`insights-server/internal/analyticsimpl/retrieve_qm_task_stats.go:185-200,272-290`). `GetTaskByID` also filters by task `usecase_id` when a use case is passed (`shared/qa/manual_qa.go:31-60`); suggestion and evaluation-period RPCs pass the request's use case to that helper (`insights-server/internal/analyticsimpl/suggest_manual_qa_conversations.go:103-119`, `apiserver/internal/coaching/action_retrieve_evaluation_periods.go:28-31`). This column is not the direct conversation-use-case predicate or a scorecard scoring rule, but it can prevent a task from being discovered or its evaluation period from loading. A task copied with A is invisible from a B-only task view even when its template covers A and B.
5. QM task-config backfill creates one task per template, skips an empty all-use-cases template, and stores `template.UsecaseIds[0]` (`cron/sync-users/internal/qm-task/backfill_qm_task_config.go:101-131`). Scorecard task-ID backfill pairs template ID with that singular task use case (`cron/sync-users/internal/scorecard-task-id/backfill_scorecard_task_id.go:68-83`). Both encode the same singleton assumption.

## Is every QM task template-based?

The normal Director QM task save path requires a loaded scorecard template, errors if absent, puts its name in `QmTaskContentConfig`, and creates or updates through `CreateDirectorTask`/`UpdateDirectorTask` (`director/packages/director-app/src/components/qa/qa-task-setting-modal/hooks/useUpdateDirectorTaskConfig.ts:53-72,185-205`). The QM task-config backfill also starts from a scorecard template and writes its ID into task content (`cron/sync-users/internal/qm-task/backfill_qm_task_config.go:85-86,101-155`). The public content model has a single template reference for a QM task (`cresta-proto/cresta/v1/coaching/task.proto:129-135`). No supported template-free QM authoring path was found in the reviewed production UI and backfill source.

This is **not yet a guaranteed storage invariant**. `CreateDirectorTask` converts and writes the supplied task without checking that a QM task has a template reference or that the referenced template exists (`go-servers/apiserver/internal/coaching/action_create_director_task.go:46-64`). The converter accepts nil QM content config (`go-servers/shared/converters/coaching/converter.go:239-257`), and `director.tasks.task_content_config` is nullable with no template foreign key or QM-type check (`go-servers/apiserver/sql-schema/director/director-schema.sql:289-307`). Therefore the API/schema appear capable of storing a QM-typed task with no template link; source review cannot prove whether such rows currently exist in customer databases. Before deriving all QM scopes from templates, measure unmatched/missing template references in relevant deployments and define how legacy rows are handled.

## Decided product invariant

Xuanyu confirmed on 2026-10-08 that a template-based QM task should share its template's whole use-case scope. Formally, for the applicable template revision T and its QM task Q, `scope(Q) = scope(T)`. The task may have its own identity and settings, but its use-case scope is inherited, not an independently editable selection. More than one task may reference T; their audiences, quotas, schedules, and conversation filters can differ without changing the use-case invariant. A concrete conversation/scorecard still has one use case U; it is eligible only when U is in T's effective scope, Q is active and otherwise eligible, and the reviewer is entitled to U. Criterion applicability is then evaluated within that concrete U. See the [decision record](../../decisions/2026-10-08-qm-task-inherits-template-usecase-scope.md).

An all-use-cases template needs an explicit **all** scope in this model; an empty repeated field must not be misread as **none**. A future task API may expose repeated use cases as derived output, or storage may materialize them for indexed queries, but a stored copy requires coherent updates when the template scope changes. Prefer one authoritative template scope and a normalized applicability/read helper; choose materialization only with an explicit update/rebuild contract and coverage for direct SQL readers.

When a template adds or removes a use case, its existing QM tasks follow the applicable current template scope for future evaluation. Previously submitted scorecards retain their own concrete use case, pinned template revision, and historical task association. Do not retroactively reassign or erase them. Deactivation/deletion and whether tasks should be suspended when a template becomes unusable need a separate lifecycle decision.

## Limits and implementation gates

- Enforce the QM task-to-template link and same customer/profile server-side on create/update, then audit legacy rows for missing or stale links. Reject a QM task scope outside the template; with current agreed behavior, require equality rather than permitting a task-only subset. A narrower task use-case choice would be a new product feature with its own quota/report semantics.
- Resolve the latest template revision when computing future eligibility and task discovery. Keep stored scorecards tied to their evaluated revision. Validate changes to template scope against task lifecycle behavior; update any task scope projection atomically or derive it at read time.
- Apply the same scope test in task list, suggestion/evaluation, periods/progress, report, and both backfills. Filter scorecards by their own concrete use case even when a task spans many. The QM Report task quota is task-level today, so a use-case-filtered count cannot be called a per-use-case completion rate without an allocation rule.
- Preserve non-QM tasks' existing use-case contract. A shared scorecard template does not imply that group-calibration tasks inherit a plural task scope.
- Migration needs explicit handling of legacy singleton task rows, templates with all-use-cases scope, and template scope edits. The source audit is not a deployed-data census or a performance validation.

## Status

This is a decided product invariant based on current source and Xuanyu's direction, not an implemented contract. The exact task API/storage shape and template-change synchronization remain open implementation decisions.
