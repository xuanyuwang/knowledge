Purpose and result

A caller supplies a customer/profile, start-time interval, supported analytics filters, optional Agent or Team grouping, and optional daily/weekly frequency. The response measures how many eligible conversations contain at least one qualifying use by an eligible agent. The client computes the percentage; a zero denominator should display N/A.

Query revision: reduce before joining

The earlier adapter applied (conversation_id, agent_user_id) GLOBAL IN (...population...) inside every feature source. Following Xuanyu’s historical performance review, the adapter now filters sources by eligible agents, reduces each family to conversation/agent pairs, and uses an ordinary population join outside that reduction. Feature predicates and copied-time semantics are preserved.

The no-GLOBAL guard failed before the revision. All seven generated queries then executed on two local shards with distributed_product_mode=deny; KB evidence qualified from either shard, and Summary generation/copy matched across shards. Plans place population matching above remote reduction; captured remote SQL has no population-table reference. This establishes the tested shape, not production speed or native-protocol byte savings. The larger historical feature-pair stream is an explicit tradeoff.

Additional review: evidence query limits
Review 5604982557 identified an evidence-query size failure and a historical-scan concern.
Agent transport: always use external data
Before: each source predicate expanded eligible agent IDs into SQL text. The permanent 8,001-agent regression failed with Max query size exceeded. Change: replace columnIn with agent_user_id IN (SELECT user_id FROM assistance_usage_agents); build a query-owned external agent table with the existing helper and attach it alongside the population table. Why: query text stays fixed while retaining source pruning and the exact outer pair join. After: the regression and full evidence suite pass; a fresh two-shard check executes all seven queries with 8,001 external agents under distributed_product_mode=deny. Remote SQL references the agent table and excludes the population table.
The earlier local benchmark measured 4.3 ms external versus 1.2 ms inline for five IDs, and 2.4 ms versus 6.5 ms for 5,000 IDs. It supports avoiding a list-size threshold; it is not a production benchmark for this API. The agent list is transferred for each query and external-table processing still costs memory and CPU.
Historical scan: distinguish copied start from event time
KB evidence copies Chats.StartedAt into conversation_start_time; the search event's own time is stored separately. A delayed event alone does not explain an October 6 copied start for an October 20 conversation. Existing PostgreSQL event IDs can be skipped during indexing, so a start-time correction plus selective refresh can leave an old event copy. No real fourteen-day correction or maximum skew has been established. The fourteen-day diagnostic was synthetic; it proves current matching accepts that mismatch, not that it is a normal valid business case. Time pruning needs the correction/reindexing contract across all seven families. Timestamp filtering is unchanged in this fix.

Effects and remaining limits
Preserved feature edges
GenAI retains source 0/8, so source-7 evidence alone does not qualify. Summary generation and copy still require equal copied start time internally. Data type 2 qualifies; type 3 does not. Notes stays copy-only. Workflow retains the existing document/session predicate.
Time semantics
Selection and buckets use population conversation start time. Buckets preserve the shared current whole-hour fixed timezone offset; historical DST and fractional-hour zones are not corrected here. Empty intervals are omitted.
Read volume and memory
Seven queries still upload the full eligible-pair table to the initiator. Source predicates carry only eligible agents; a normal join intersects reduced feature pairs with the population. Two-shard execution and plans validate this shape locally. Historical rows for selected agents can increase reduced-pair transfer before the join; no timestamp partition bound is applied. Concurrency three bounds simultaneous queries, not total memory or latency. Native network volume and representative production performance remain unmeasured. A follow-up Linear ticket candidate covers frontend/backend coordination to reduce total queries per page interaction; the end-to-end request/query baseline is still to be measured.
Compatibility and rollout
No stored schema changes. Existing feature RPCs and predicates are untouched. This endpoint alone enforces explicit agent/activity restrictions. Director, details, feature timing instrumentation and release validation remain pending.
Findings addressed during implementation
The unrestricted-user optimization was proven to overcount restricted audiences and fixed at the new endpoint boundary. Query mocks now allocate independent nonempty rows per concurrent query. Summary uses an explicit inner join of shared CTEs rather than modifying a relation string. Restricted population reads force external user tables after 8,001-user regressions reproduced SQL size failures with the shared flag off. Evidence queries also use external agent tables for every nonempty population, with an 8,001-agent regression and fresh two-shard execution check. No confirmed unresolved counting-correctness blocker remains within the scoped preservation boundary.
Non-blocking maintainability
The Summary adapter names the shared generation/copy CTEs directly. A typed relation helper would reduce that coupling if more consumers appear. Team bucket merging rebuilds a small lookup per agent; optimize only if measurements identify a cost.
