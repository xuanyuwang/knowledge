# Multi-use-case criteria and AutoQM rule mapping

- Date: 2026-10-08
- Primary subdomain: template-authoring-and-versioning; related: evaluation-and-scoring
- Primary source repo: `/Users/xuanyu.wang/repos/go-servers` (`main`, `435cb9047a`, read-only)
- Related source repo: `/Users/xuanyu.wang/repos/director` (`main`, `f47845f4f7`, read-only)
- Product input: Omni Use Case QM / Coaching PRD wording supplied by Xuanyu: multi-use-case AutoQM criteria should attach multiple Opera rules across use cases, detect duplication involving global rules, and handle only a subset of use cases being AutoQM-able.

## Answer

The PRD's “AutoQM criteria” refer to regular scorecard criteria with AutoQA configuration, not a distinct criterion type. Today the `auto_qa` object lives inside an ordinary numeric/labeled/dropdown criterion in version-2 template JSON. Its `triggers` array holds `{type, resource_name}` entries for behaviors (the current Opera-linked picker), with legacy policy and other trigger types also supported. The template's `usecase_names` API field and persisted `usecase_ids` are outside this JSON and apply to the entire template. Neither a criterion nor a trigger has a use-case field today.

Adding criterion-level use-case scope to the regular criterion model is the right way to say where the criterion exists for manual and automatic evaluation. Where `enableGlobalOperaRule` permits it, a single Opera policy can apply to multiple selected use cases or the `all-usecases` sentinel, and its behavior inherits that scope. A shared rule can therefore serve A and B for those customers. Without that authoring flag, separate A-only and B-only rules may need to attach to the same criterion. When a rule covers only A while the criterion covers A and B, the Opera rule's existing scope says where it is eligible, but the current AutoQA scorer does not consult that scope. It sees only the behavior's annotations for the conversation. A warning alone does not make the no-rule-in-B case semantically correct: absence of evidence becomes N/A (and may produce an N/A item when `showNA` is enabled). The implementation needs an effective AutoQA applicability check, which could derive scope from the referenced behavior/policy or use a versioned mapping in template JSON. The representation remains a design choice.

## Source trace

4. `go-servers/shared/scoring/scorecard_template_dao.go:58-66,188-221` filters templates by the concrete conversation use case. `apiserver/internal/autoqa/action_calculate_conversation_autoscoring_evidence.go:72-103,191-214` then passes the selected template's *entire* `GetAutoScorableItems()` list to scoring; there is no criterion or trigger use-case filter. `shared/scoring/autoqa_scoring.go:41-105,149-183` evaluates every trigger and combines evidences into one criterion outcome; the mapper's options path can count evidences (`shared/scoring/autoqa_mapper.go:53-68`). `autoqa_scoring.go:83-85` skips a no-evidence N/A result only when `showNA` is false. `action_calculate_conversation_autoscoring_evidence.go:209-215` marks a template auto-scored when at least one item is returned, and `action_trigger_conversation_autoscoring.go:168-186` otherwise skips creation.
5. `go-servers/apiserver/internal/policy/validator.go:395-435` rejects a behavior ID used by another policy, regardless of use-case overlap. That ownership guard does not detect two *distinct* behavior IDs that represent the same criterion in an overlapping global and specific use-case rule. `GetAutoQATriggers()` deduplication is by identical resource name, not by semantic overlap. There is no template-level duplicate or precedence rule for a global behavior plus use-case-specific behaviors.

## Recommended model boundary

- Keep one template-owned, versioned criterion with its own none/all/some applicability as proposed in the core multi-use-case model. Its ID, scoring options, weight, and manual editing semantics remain one criterion.
- Keep AutoQA configuration optional on that criterion. Where the authoring flag allows it, a single referenced behavior may cover several use cases, including all. Also support multiple use-case-specific rule references on one criterion for customers without that flag. Do not require duplication when one shared rule already covers the scope. Validate the effective behavior/policy scope against the criterion and template scope, and decide whether AutoQA applicability is derived from the current Opera rule or snapshot in the template revision. Preserve historical trigger entries through a documented legacy default.
- For a concrete scorecard use case, first select applicable criteria, then determine which referenced triggers' Opera scopes cover that use case. A criterion can remain manually scorable where no trigger is eligible. Do not treat an ineligible trigger's missing annotations as an AutoQM N/A score; whether a scorecard with zero AutoQM items should exist is a separate product rule.
- Define global/specific overlap before choosing a combining rule. If global and specific triggers describe the same logical assessment, either reject ambiguous overlap or explicitly choose precedence. Blindly evaluating both can change detected/not-detected outcomes or occurrence counts. Validate duplicate resource names and semantic collisions, including global-plus-specific cases; the policy ownership guard alone is insufficient.
- Update the builder to load the template's full use-case behavior set, support multiple mapped selections, and validate and display mappings. Update typed Go parsing/serialization, Create/Commit validation, template trigger indexing, AutoQM runtime filtering, and readers that assume `triggers[0]` (frontend validation, score mapping, display-name resolution, and `shared/scoring/scorecard_scores_dao.go:415`). Preserve revision-pinned interpretation for existing scorecards.

This is a source-based design assessment, not an implemented contract. The exact source of truth for effective trigger applicability (derived Opera scope versus template-revision snapshot), legacy default, duplicate definition, and AutoQM behavior in a use case with no eligible rule still need explicit decisions.

## Product follow-up from Xuanyu

Xuanyu confirmed the remaining issue is the gap between criterion use-case scope and linked Opera rule use-case scope. Keep two product options open: (1) auto-score only on the intersection, leaving the criterion available for manual scoring in the other use cases, or (2) warn/require the author to provide eligible rules across the criterion's scope. A shared rule may provide that coverage where authoring is enabled; separate rules may provide it otherwise. A warning alone cannot be the full runtime solution while the scorer treats absent annotations from an ineligible rule as N/A. This is an open decision, not approval of either option.

## 2026-10-09 design correction

Xuanyu clarified that `enableGlobalOperaRule` is available to only a few customers by his current understanding; that rollout size has not been independently verified. The source confirms the flag gates the multi-use-case picker in Director's `ReviewPolicySection.tsx`. Therefore a single shared Opera rule cannot be assumed as the normal authoring path. A shared criterion across A+B should be able to reference distinct A-only and B-only Opera rules. The JSON `auto_qa.triggers` array can hold both references, but `TemplateBuilderAutoQA.tsx` currently reads `triggers[0]` and replaces the array with zero or one trigger, so authoring and save/read consumers need changes. Runtime must select rules eligible for the concrete conversation use case before treating absent annotations as N/A; global-plus-specific overlap needs an explicit policy. A single A+B rule remains a supported option where the flag is enabled. Updated both engineering drafts with this baseline and kept uncovered-use-case behavior open.
