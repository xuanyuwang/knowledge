# Agent Leaderboard — Active Days Behavior Guide

Last reviewed: 2026-07-22

# 1. Feature Behavior

## What Active Days Means

A day is considered active when Cresta can confirm that an agent was online while handling at least one included conversation.

The determination depends on whether the conversation contains messages sent by an agent:

### Conversations with agent messages

The day is active when at least one message was sent by the agent while that agent was shown as online in Cresta.

The activity is counted on the day the matching message was sent.

### Conversations without agent messages

This includes conversations containing only customer messages or no messages.

The day is active when the assigned agent was shown as online at either:

- The start of the conversation, or
- The end of the conversation.

The activity is counted on the day the conversation started.

In both cases, the conversation must be included by the selected filters and customer configuration. For example, a conversation from an excluded source cannot make the day active.

## Where Active Days Appears

Active Days appears in two places in Performance Insights:

- **Statistics widget:** The average number of Active Days per agent during the selected time range.
- **Agent Leaderboard:** Each agent's Active Days result, represented by `1`, `0`, or `N/A` for a given day.

## How to Interpret the Values

| Value | Meaning | Effect on averages |
|---|---|---|
| `1` | The agent had a qualifying conversation and qualifying Cresta activity evidence that day. | Included |
| `0` | Cresta found relevant activity, but it did not meet the Active Days requirements. | Included and lowers the average |
| `N/A` | Cresta did not find enough relevant information to evaluate that agent for the day. | Excluded |

The difference between `0` and `N/A` is intentional:

- `0` means the day was evaluated and did not qualify.
- `N/A` means the day could not be evaluated.

## Common Examples

An agent will generally receive `1` when:

- They had at least one qualifying conversation.
- Cresta found evidence that they were online while participating in the conversation.

An agent may receive `0` when:

- They had qualifying conversations but no matching online activity.
- Their only activity came from a conversation source excluded by the customer's configuration.

An agent may receive `N/A` when:

- Cresta has no relevant conversation or activity evidence for that agent and day.
- The agent handled conversations outside the workflow measured by Active Days.

## Conversation-Source Configuration

Some customers exclude Ingestion Pipeline conversations from Agent Leaderboard activity.

When these conversations are included, they can contribute to an Active Day.

When they are excluded:

- They cannot make an agent's day active.
- Existing evidence may still cause the day to display `0`.
- They will not incorrectly produce a value of `1`.

## Important Limitations

Active Days is based on evidence that an agent was online in Cresta. It is not a direct measurement of whether the agent actively used a specific feature.

Consequently:

- Missing or delayed online signals may cause qualifying activity to be missed.
- An online signal may qualify even if the agent did not actively use Agent Assist during that conversation.
- Current-day results may be delayed while activity is processed.
- Low adoption of the Cresta application can produce many `N/A` values even when agents are handling conversations.

When investigating unexpected results, first confirm:

1. The agent used the expected Cresta application.
2. The agent had qualifying conversations during the selected period.
3. The selected filters include those conversations.
4. The customer's conversation-source configuration matches the expected behavior.
5. Enough time has passed for current-day activity to be processed.

# 2. Engineering Reference

## Data Sources

Active Days uses two primary ClickHouse data sets:

- `conversation_d`: Closed conversations, agent assignment, use case, source type, and the denominator for valid agent activity.
- `conversation_with_labels_d`: Agent Assist evidence generated by `cron-label-conversations`.

Relevant conversation sources are:

| Source | Meaning |
|---|---|
| `0` | Normal conversation |
| `7` | Bot conversation, when enabled by the request or configuration |
| `8` | Ingestion Pipeline conversation |

## Label-Generation Behavior

`cron-label-conversations` processes closed conversations whose `ended_at` is within the batch range.

The job:

1. Fetches Normal and Ingestion Pipeline conversations.
2. Excludes development users.
3. Fetches messages where `speaker_role = 'agent'`.
4. Looks up messages by `conversation_id` without restricting message timestamps to the batch window.
5. Processes conversation IDs in groups of 10,000 to avoid PostgreSQL's 65,535-parameter limit.
6. Fetches online events using the batch window plus a three-hour buffer.
7. Writes one label row for each agent message whose timestamp overlaps an online event for that agent.

For message-level rows:

- `message_id` contains the stable conversation-message ID.
- `message_agent_user_id` contains the message's agent ID.
- `message_time` contains the message's `platform_timestamp`.
- `has_agent_assistance` is `true`.

The absence of a message-time restriction during message lookup is intentional. A multi-day conversation processed according to its end time can contain valid agent messages from before the batch began.

## Conversations Without Agent Messages

For conversations without agent messages, including visitor-only conversations, the job writes a fallback row with `message_id = ''`.

The fallback uses conversation-level matching:

- `has_agent_assistance = true` when the assigned agent was online at the conversation's start or end time.
- Otherwise, `has_agent_assistance = false`.

These rows keep the processing watermark moving and preserve these conversations for downstream analytics.

## Leaderboard Read Path

`RetrieveAgentStats` constructs two ClickHouse CTEs:

- `convs`: Counts distinct agents from `conversation_d` while applying source filters.
- `convs_with_aa`: Counts distinct agents from `conversation_with_labels_d` where `has_agent_assistance = 1`.

The CTEs use a `FULL OUTER JOIN`, and missing counts are converted to zero with `COALESCE`. This preserves agent-day rows when only one data source contains evidence.

Time attribution is:

- Message-level rows: `message_time`
- Legacy or fallback rows with `message_id = ''`: `conversation_start_time`

When Agent Assist conversation count is enabled, `active_agent_count` is used only when `total_agent_count > 0`. This prevents excluded Ingestion Pipeline evidence from producing an Active Day.

## Ingestion Pipeline Exclusion

Configuration: `exclude_ingestion_pipeline_from_agent_stats`

When disabled:

- Normal and Ingestion Pipeline conversations count toward valid activity.
- Either source can contribute to an Active Day.

When enabled:

- Only Normal conversations contribute to `total_agent_count`.
- Ingestion Pipeline labels may remain in `conversation_with_labels_d`.
- Ingestion-only evidence produces `0`, rather than `1`, because of the `total_agent_count > 0` guard.

## Conversation Stats Difference

Conversation Stats answers whether an entire conversation had Agent Assist. It therefore scopes results by conversation time rather than message time.

- Agent Assist ON: Uses `max(has_agent_assistance)` across label rows belonging to the conversation.
- Agent Assist OFF: Starts from `conversation_d` and uses a `GLOBAL LEFT ANTI JOIN` to remove conversations with any true label row.

This supports both legacy conversation-level rows and newer message-level rows.

## Debugging Checklist

When an Active Days value appears incorrect, verify:

1. `conversation_d` contains closed conversations for the agent, day, use case, and source filters.
2. Whether `exclude_ingestion_pipeline_from_agent_stats` is enabled.
3. `conversation_with_labels_d` contains the expected label rows.
4. Whether each row is message-level or fallback/legacy.
5. `message_time` falls within the requested day for message-level rows.
6. `conversation_start_time` falls within the requested day for fallback or legacy rows.
7. The labeling job or backfill ran after the conversation closed.
8. The available evidence is not exclusively from an excluded source.
9. Agent assignment and use-case metadata reflect the conversation's final state.
10. Online-event and heartbeat coverage exists for the agent.
