What the PR does

When the rollout flag resolves true, Assistance Used loads per-agent and per-team conversation usage statistics, merges them with existing rows, and exposes a configurable percentage column and CSV field. Zero use stays zero; unavailable values show N/A. Off/unresolved states must not request or expose this metric.

Rollout flag → grouped API results → row merge → table / tooltip / column menu / CSV

How the behavior grows

These are reconstructed explanatory stages, not separate commits.

Baseline: legacy assistance rows and metrics
Add gate + API: enabled = isResolved && value; withhold cached results otherwise
Merge: insert eligible usage-only agents; retain name, username and percentage
Display: sticky column + tooltip + configurable visibility + numeric CSV

The final stage introduces the hidden-width and keyboard-access concerns. Inserting usage-only rows exposes the team metadata omission.

1. Sticky header width after hiding the metric

With both the metric rollout and configurable-columns flags enabled, a user hides the new 80px column. TanStack removes its visible leaf, but the hooks still store its width in the sticky parent group. DirectorTableHeader applies that stale width to the grouped header; body offsets use visible cells.

Proposed fix

Recalculate the sticky parent group’s fixedWidth from visible child definitions before passing columns to each DirectorTable. Keep the original definitions for the column menu so the metric can be shown again. Put this in a local Assistance Used column helper, rather than changing all Director tables. The configurable-menu helper alone cannot fix it because it does not receive hidden-column state.

Validation and limits

Hide/show the metric in both tables with configurable columns enabled. Assert group width equals the sum of visible sticky leaf widths and restores on show. Check horizontal scrolling in a browser. The 80px metadata mismatch is executable-model evidence; actual browser pixel layout has not been checked.

Valid; accessibility defect

2. Keyboard access to the definition tooltip

SharedTooltip attaches its focus handlers to the child span. The span has no tabIndex, so Tab cannot focus it. The surrounding sortable header button is focusable, but focusing an ancestor does not dispatch focus to this child. Thus sorting remains keyboard accessible while this explanation is not.

Proposed fix

Add tabIndex={0} to both tooltip trigger spans as the minimal fix. Keep the shared tooltip’s focus and Escape handling. Avoid inserting another button inside the existing sortable header button. A future table-level API could attach the tooltip to the actual sort control, but is unnecessary for this PR.

Validation and limits

Verify with Tab that both explanations open, Escape dismisses them, and sorting still works. This conclusion is based on the rendered element hierarchy and SharedTooltip implementation; no browser keyboard run was performed.

3. Team metadata missing from usage-only agent rows

The new result can create an agent absent from legacy assistance results, including an eligible agent with zero usage. Row creation initializes team to an empty string. The usage merge fills name, username and percentage but never team. A supplied user.teamDisplayName="Support" is consequently lost. The API transformer retains this metadata, so it can reach this path.

Proposed fix

In the usage-result merge, fill only a missing team: row.team ||= user?.teamDisplayName || group?.displayName || ''. This preserves an existing legacy team and keeps the fix local to the new merge. The reviewer’s broader change to the shared row factory would work but also changes other legacy row-creation paths.

Validation and limits

Cover a usage-only agent with user team metadata, grouped-team fallback, neither field present, and a legacy row whose non-empty team must remain unchanged. Do not invent a team when the backend supplies none.

Accurate observation; minor display consistency improvement

4. Percentage cells omit the percent sign

For a rate of 37.5 the current renderer returns "37.5"; for zero it returns "0.0". Most neighboring engagement/usage percentage cells include %. The header already contains %, so the number itself is correct and this is not a calculation error. Another adjacent AA percentage also omits the suffix, so the convention is not universal.

Proposed fix

Use the existing locale-aware formatter for this new metric in both tables: rate === undefined ? 'N/A' : fmtPercentage(rate / 100, { numDecimals: 1 }). The adapter already stores a 0–100 percentage, whereas fmtPercentage expects 0–1. Keep CSV values numeric (37.5), with (%) in the CSV heading.

Validation and limits

Check 37.5 → 37.5%, 0 → 0.0%, and undefined → N/A in the active locale. Ensure the CSV remains 37.5 rather than a decorated string. Do not change unrelated legacy percentage columns.
