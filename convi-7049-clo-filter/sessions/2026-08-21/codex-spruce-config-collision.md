## Effective-state correction

The initial fleet audit counted `customer_config_history`, not effective ConfigService state. That distinction explains the Admin report of 249 disabled profiles.

- Uber, Twilio, and eBay each have `enableCLOFilters: true` in current `customer_config_history`.
- Their current ConfigService-derived `configv3/prod/.../frontend.yaml` files have no `enableCLOFilters`.
- The same split exists broadly: current `configv3/prod` has only 46 frontend configs containing the enabled flag; the rest are absent. The Admin page's reported 249 disabled profiles is a narrower UI-filtered subset, and its 46 enabled count aligns with generated state.
- Therefore the 11-customer number measured only where later writers had already made the Git history catch up to the absent effective state. It did not measure the rollout's effective coverage.
- The meaningful status is the Admin/ConfigService profile count: 249 disabled in the user's selected scope. The unresolved root cause is why batch sync reported successful persistence while the effective/read-back state did not retain the flag.

## Workflow model and failure boundary

1. A PR edits `customer_config_history/**`, the desired full-customer snapshots.
2. On the PR, `Batch sync to config service` runs with `diff_only=true`. It calculates and comments the prospective ConfigService diff but does not persist.
3. On merge to `master`, the same workflow runs with `diff_only=false`. It resolves changed files since the latest successful sync, sends each customer only to its Config DB home cluster, persists batches of ten, then dispatches Flux and Terraform customer regeneration.
4. Independently, `Sync From ConfigService` runs every four hours and reads every ConfigService cluster back into `configv3`, creating and auto-merging a PR.
5. A `configv3` push triggers `sync-to-v2`, which regenerates `customerv2`, `walter-public`, and `hermes-public`.

Important operational properties:

- The push workflow uses `cancel-in-progress`; a newer push can cancel an active sync, as happened for the later Spanish recovery. It did not cancel the original CLO GA run.
- A green batch workflow only proves the Mage command returned success. It performs no post-write round-trip assertion that every desired field appears in ConfigService or subsequent `configv3`.
- The scheduled readback overlapped the CLO GA run, but later readbacks still omit the values, so a one-time stale read cannot explain current state.
- Pilot entries survive in `configv3`, proving the readback format can represent `enableCLOFilters`. The unproven failure boundary is therefore narrowed to bulk persistence or a later DB-side overwrite, rather than a universal readback-conversion omission.
- Later full-customer Admin/profile-health-check writes use effective state without the flag and then remove the history-only value when their generated PRs merge.
