# Roles in ListUsersForAnalytics: evidence and recommendation

Date: 2026-11-01 (America/Toronto). Investigation only; the design below is proposed, not implemented or approved for rollout.


User decision, 2026-11-02: implement only the per-membership `AuthProto.Role` field first. Defer `custom_roles`; the two-field proposal below remains historical option analysis. This step is a protobuf-only PR for CONVI-7852.

## Recommendation

Add per-membership `roles` (`AuthProto.Role`) and `custom_roles` (role resource names) to the internal `UserGroupMembership`, with explicit semantics: these are assignments on direct memberships; indirect memberships do not contain resolved inherited roles. Keep `LiteUser` global roles out of this change because the demonstrated Agent-team use case does not need them. Keep the existing analytics population and all filters, ACL decisions, membership mappings and totals unchanged.

For CONVI-7852, consume the metadata only when selecting the singular Agent-tab display team: prefer a direct TEAM carrying the old-system AGENT role among that row's existing analytics groups, choose the lowest resource ID, and retain the original first group otherwise. Retain the complete groups array and existing Team/Manager behavior. A Team Leaderboard rule that counts a user only where they have AGENT is a separate metric policy; current evidence does not authorize it.

Adding fields to the internal RPC alone cannot remove the Director lookup. Roles must also survive the insights response construction. Prefer using the already-existing public `User.group_memberships` field on per-agent conversation-stat rows, followed by the existing Director display selector. Carry role metadata separately from query-filter User objects, intersect it with the final eligible users, and attach only direct candidate TEAM memberships at response construction. Apply this decoration consistently to fresh and cached responses without mutating shared cache objects. This avoids adding a new public reporting-team field and keeps display selection in the Agent page.

### Concrete use cases

1. **Required and already agreed: Agent display and CSV.** With `team-a: MANAGER_2ND` and `team-b: AGENT`, where a sorts first, display b without altering the user's metrics or memberships. With b and c both AGENT, display the lower ID. With no matching direct AGENT team, preserve a. This needs team-specific roles, not global roles.
2. **Existing role-aware reporting: formal Manager association.** Director's Manager page maps team members carrying MANAGER (`ManagerLeaderboardPage.tsx:197-213`). Manager 2nd is not interchangeable. This proves that roles have reporting meaning, but does not justify migrating that existing data path in this change.
3. **Existing global eligibility: Agents only.** Auth tests `auth.users.user_roles` for nonempty and no value other than AGENT (`action_list_users_for_analytics.go:131-136`). Returning global role metadata is not necessary to preserve this server-side filter. Do not replace it with “has AGENT somewhere.”
4. **Possible future Team aggregation: explicit product choice.** With a user having 10 qualifying conversations, direct AGENT in B and MANAGER_2ND in A, current mappings can attribute 10 to both A and B. AGENT-only attribution would make A zero; single-primary attribution would additionally remove contributions from other Agent teams. Hierarchy rollups can also change. These are different metrics, not consequences of adding response metadata.

## Role distinctions

| Concept | Source | Meaning for analytics |
| --- | --- | --- |
| User-wide old-system roles | `auth.users.user_roles`, public `User.roles` | Cumulative role information without team provenance. A global AGENT cannot establish that a particular membership is AGENT. Customer-wide role arrays should not be described as profile-local. |
| User-wide new-system roles | `auth.users.custom_role_ids`, public `User.custom_roles` | Custom-system role IDs across team memberships; returned as typed role resource names. Again no team provenance. |
| Direct membership old-system roles | `auth.user_group_memberships.role_id` | Decimal strings representing `AuthProto.Role`, not the separate deprecated `LegacyAuthProto.Role`. Correct input for the already-approved AGENT display rule. |
| Direct membership new-system roles | `auth.user_group_memberships.role_ids` | IDs from the custom-role system, which includes both Cresta-defined and customer-defined roles. Preserve them as `customers/{customer}/roles/{role}` names, not labels or numeric enums. |
| Indirect membership | `auth.user_group_memberships_all` | The view deliberately returns empty `role_id` and `role_ids` on indirect rows. Empty here means inheritance is not represented, not that the user has no effective role. |
| Resolved inheritance | Public `ListUserGroupMemberships`, `action_list_user_group_memberships.go:81-146` | Separately loads group role assignments and retains origin/path information. Copying two columns from the analytics view does not implement this contract. |
| Custom role inheriting a base role | `auth.roles.source_role_id`; role converter `auth/shared/model/converter/converter.go:142-147` | Inheritance and permissions exist, but a custom name or permission set must not be guessed to mean AGENT reporting designation. `crestarole/role_definitions.go:60-94` defines the built-in mapping, including `custom_agent`. |

Public `ListUsers(include_user_memberships=true)` also reads the reduced-membership view (`action_list_users.go:125-145`) and converts its arrays (`auth/shared/model/user.go:248-263`). It therefore carries direct assignments, but its indirect roles are not equivalent to the separately resolved single-user membership API. A direct and an indirect row for the same user/team can coexist because the view uses UNION ALL; do not merge those by team ID and accidentally promote an indirect role into a direct assignment.

## Implementation options

| Option | Advantages | Costs and risks | Recommendation |
| --- | --- | --- | --- |
| Keep Director targeted public enrichment | Already implemented locally; no backend rollout dependency | Extra paginated read, asynchronous label changes, public ACL can omit metadata | Keep the validated worktree intact while evaluating the backend option. |
| Add direct membership metadata internally; pass candidate memberships on Agent response Users | Reuses existing population and existing public field; eliminates redundant public fetch once consumed | Auth/proto/insights/Director rollout, payload cost, cache handling, two current metadata drops | Preferred long-term approach for the demonstrated need. |
| Add global roles only | Simple user projection change; useful for a future proven global-role consumer | Cannot resolve which team carries AGENT; adds unrelated payload | Insufficient for CONVI-7852. Defer until a concrete global-role response use case exists. |
| Resolve effective inherited roles and change Team rollups | Can support future role-aware hierarchy metrics | Needs path/provenance semantics, batched role assignment reads and explicit new aggregation policy; much more than exposing existing columns | Separate investigation and product decision. |

Proposed delivery sequence: release additive internal proto fields; populate auth fields and version its cache; carry metadata through the eligible-user result without changing filter objects; decorate only per-agent conversation response Users with direct memberships intersected with the row's candidate groups; reuse the Agent display selector against inline metadata; remove the public lookup only after mixed-version fallback and full request coverage are verified. This is a proposed sequence, not authorization to edit source or publish changes.

Initially always return the two direct-assignment arrays: they come from the existing membership query and do not need another round trip. Retain the smart projection. Measure SQL scan time, allocations, serialized page bytes, Redis bytes and RPC latency before deciding whether an opt-in field is needed. If opt-in is chosen, include it in cache keys and request it consistently on every page. There is no performance proof in this investigation.

## Cache and compatibility

- Auth caches JSON-encoded LiteUser pages for five minutes by default; page size defaults to 3,000; named user IDs bypass cache. The cache key includes customer/profile/group/offset/activity/agent-only but no schema version (`action_list_users_for_analytics.go:281-326`, `cache.go`). Additive fields decode as empty from old entries. Version the logical key before hashing so both hash-enabled and hash-disabled modes separate old/new payloads. Old and new server versions can coexist: old RPC responses still lack metadata and must retain the old display fallback.
- Metadata is a current membership snapshot, not membership at the historical conversation date. Preserve existing current-membership behavior; historical attribution is separate work. Role edits can remain stale through the auth TTL.
- Conversation stats have their own optional API cache. `RetrieveConversationStats:83-90` returns cached responses before response conversion; configured maximum age defaults to four hours (`api_cache.go:57`). Simply enriching the CH converter leaves warm responses without metadata. Prefer decorating both cached and fresh responses using the already-filtered current metadata and cloning response objects. Alternatively version the stats cache and accept/document its role staleness. Do not change numeric cached metrics as part of display enrichment.
- Internal protobuf additions are wire-compatible but semantic availability is not guaranteed during rollout. New auth with old insights has no display effect. New insights with old auth must fall back. Old clients ignore added fields. Generate/release the proto package; do not hand-edit generated clients. Existing public membership fields can avoid a new public proto/client release, but verify the locked Director client and transformer behavior.
- Repeated empty role arrays cannot distinguish a legitimate empty direct assignment from an old producer. That is acceptable for this display fallback, but cannot prove “no effective permissions.” Future effective-role filtering needs explicit completeness/provenance semantics.
- Do not change role filtering, user_types handling, group union/intersection, root/default behavior, ACL paths, pagination, returned IDs or ordering. Current internal handler does not apply its proto user_types field; that existing discrepancy is not repaired here. Public ListUsers applies caller ACL and uses any-role overlap; internal AgentOnly uses exactly-Agent semantics.
- Expose only memberships already appropriate for the eligible user's response and row's existing candidate groups. Do not infer that membership metadata grants access, expose all customer memberships on every analytics endpoint, or populate User.roles with membership-specific values.

## Meaningful implementation tests

These are proposed tests, not executed results. Use real local Postgres for auth view/handler behavior, existing suites for service wiring, exact business-field proto comparisons, and Given/When/Then. Do not mock the DB view.

1. Auth: one user with A=MANAGER_2ND and B=AGENT; assert separate per-membership arrays and custom resource names, unchanged user IDs/names, groups/directness and pagination offsets. A second user in another tenant with matching IDs must not leak data.
2. Auth view: direct and indirect membership to the same team, nested parent, and a role-bearing dynamic-group assignment. Assert direct roles stay on the direct row; indirect arrays remain unresolved/empty even if the separate public API could resolve an inherited role. Preserve active-group, managed-group and profile exclusion.
3. Auth compatibility: missing old-role array, custom-only assignment, multiple roles, malformed numeric legacy-system role IDs and unknown numeric values; match established public conversion behavior. No custom label-to-AGENT heuristic.
4. Auth filters: frozen user sets for active/inactive, profile, group with/without indirect eligibility, user IDs plus group intersection, exactly-Agent versus mixed roles, and zero results. All existing identities and counts must remain identical with metadata populated.
5. Auth cache: cold then warm role round-trip; all pages, named-ID cache bypass, old JSON payload fallback, key version isolation with hashing on and off, mixed old/new producers, and documented stale-until-expiry role changes. Keep pending/ready behavior intact.
6. Insights: metadata reaches the final response row for fresh and stats-cache-hit responses; ACL-disallowed users and out-of-profile/candidate memberships are absent. Query filters, mappings, full group ordering, SQL population and all numeric fields compare equal before/after. Returned objects and cached objects are not mutated across requests.
7. Display: Agent A/Manager B, deterministic multi-Agent ties, no Agent fallback, global AGENT but no matching team assignment, indirect AGENT only, custom-only role, empty/single group, missing metadata/old producer, shuffled input, root/default policy, selected-team filters and cross-profile groups. Assert singular label changes while original groups and stats remain identical.
8. Team regression with explicit fixture counts: dual-role user contributes 10, ordinary agent contributes 5, parent/child and multiple direct Agent teams. Assert existing per-team contributions, team size/denominators and overall totals stay unchanged. Team totals can overlap; do not assert their sum equals overall unless that metric's contract requires it. Manager page behavior remains unchanged.
9. Director: both Agent tables and CSV consume inline metadata; QA-only and ALO paths keep existing behavior. Network assertion verifies no replacement public ListUsers call is needed for conversation rows once inline metadata is available. During rollout any retained fallback lookup must still be targeted and paginated.
10. Performance acceptance: compare equal eligible user sets and responses first, then cold/warm end-to-end traces with realistic users and memberships/page. Report response/Redis size, allocations and latency. Fewer logical reads or pages alone are not evidence of lower latency.

## Product questions for subsequent work

- Does Team attribution mean all current memberships, only teams where the user is Agent, or one designated reporting team? Should ancestor rollups remain? Does the same rule apply to team size, QA, assistance, performance and conversation metrics? No change is justified yet.
- Should a customer-defined role inheriting Agent count as the Agent reporting designation? Do built-in custom_agent assignments count when the old-system role array is empty? The approved implementation currently checks AuthProto.AGENT; changing that needs an explicit mapping policy.
- Should indirect Agent assignments qualify in any future display policy? The approved rule says direct, so no inheritance resolution is needed for CONVI-7852.
- Are current membership snapshots acceptable for historical ranges? Existing behavior is current-time mapping. As-of attribution requires historical membership data and another design.
- Is auth's cache TTL acceptable for role label changes, and which analytics responses should expose the metadata beyond the demonstrated Agent conversation rows?

The existing choices for Agent ties, zero candidates and manager-only fallback are already answered. Do not reopen them or introduce a new hierarchy heuristic.
