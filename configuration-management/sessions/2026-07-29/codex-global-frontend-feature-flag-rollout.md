## Question

What is the established practice for enabling a Director/frontend feature flag in production for all customers?

## Conclusion

Use the Cresta Admin / Tenant Admin Director Feature Flags bulk editor to generate a reviewed config PR. Select the production region, find and select the flag, choose **Enable / Disable**, set the value to `true`, use **Auto Inheritance**, select all production profiles, and apply. Review the generated PR before merge.

The implementation does not set one wildcard global value. It expands the change into `customer_config_history/prod/customers/*.yaml` at profile and use-case scopes. For an actual all-customer rollout, verify coverage semantically rather than trusting the PR title or the first ten customers shown in its body.

The selector loads active profiles (`includeInactive: false`), so “all customers” through this UI means all active production profiles returned for the chosen region. Handle any intentionally excluded or inactive configs explicitly.

### GitOps behavior

`config/.github/workflows/sync_to_config_service_batch.yaml`:

- PRs touching `customer_config_history/**` run with `diff-only=true`;
- a merge/push to `master` switches diff-only off;

## Recommended checklist

1. Confirm the flag is already defined in `src/CustomerConfig.ts` and deployed to the frontend.
2. Prove the behavior on staging or a canary customer first.
3. In Cresta Admin’s Director Feature Flags page, choose production, switch to **All Flags** if needed, and select the flag.
4. Click **Enable / Disable**, set `true`, choose **Auto Inheritance**, leave the customer filter unrestricted, and select all profiles.
5. Record explicit exclusions, if any, in the PR body.
6. Review that only the intended flag changed under `customer_config_history/prod/customers/`.
7. Count expected customers, profiles, and use cases and verify every included scope resolves to `true`; verify exclusions and staging are untouched.
8. Require successful YAML/schema checks and the PR’s diff-only ConfigService sync.
9. Merge, then verify the post-merge ConfigService sync and smoke-test representative production tenants.
10. Roll back by generating the inverse bulk update (`false`) and merging its config PR.

After the repository sync catches up, use `docs/enabled-feature-flags.csv` as an additional coverage check. Defaults in `magefiles/configwizard.go` apply only when creating new customers; changing them does not retroactively enable a flag for existing production customers.

## Important distinction

The “Add Director Feature Flag” GitHub Action only adds the schema declaration and generated schema artifacts. It does not enable the flag for customers. Customer enablement is a separate Config Admin/config PR.

Production Director flags are resolved from customer config and should not be rolled out through GrowthBook, `flagd`, or `flux-deployments`. GrowthBook/local overrides are useful for development and testing only. If backend behavior must match the UI, gate both paths from the same customer-config flag; a frontend-only gate can otherwise expose actions that the backend rejects.
