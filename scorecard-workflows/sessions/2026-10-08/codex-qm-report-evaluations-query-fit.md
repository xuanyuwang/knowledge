## Query findings

1. `RetrieveQMTaskStats` parses repeated use-case names and lists current templates by array overlap, but `getQMTasks` filters singular `director.tasks.usecase_id IN (...)` (`retrieve_qm_task_stats.go:104-247,272-301`). A task shared by A and B stored under A disappears for a B-only filter. Task discovery and `qa.ListEvaluationPeriodsForTask` / `qa.GetTaskByID` have the same singular-column issue (`shared/qa/manual_qa.go:31-80`). This is a task model/query change, not a criterion-JSON query problem.
2. The **overall chart** calls `fetchScorecardsCountGroupedByFrequency`, which selects scorecards by template/task/time but has no `scorecards.usecase_id` predicate (`retrieve_qm_task_stats.go:355-433,970-991`). The **task-cycle table** calls `fetchScorecardsForPeriod`, which has the same omission (`:304-353,769-800`). After shared tasks are discoverable, B-only report results can include A scorecards. Add the selected scorecard-use-case predicate before aggregation in both branches. The no-task row's `fetchScorecardsCountForTimeRange` already applies `usecase_id IN (...)` (`:435-475`), so branches currently disagree.
3. `RetrieveManualQAStats` accepts a list of use cases. Its count, detail, and overwritten-criteria SQL each add `scorecards.usecase_id IN (...)` (`retrieve_manual_qa_stats.go:1271-1345,1348-1452,1455-1545`). The period and audience helpers still reach singular task lookup (`:1028-1055,2158-2177`; `shared/qa/manual_qa.go:31-80`). Multiple use-case filtering is feasible in the scorecard SQL after task lookup is fixed.
4. Export-only `computeExportStats` reuses the correctly scoped manual-QA scorecard detail and overwritten-criteria queries (`retrieve_qm_task_stats.go:827-895`). Its *ordinary* evaluated, acknowledged, published, and average-score fields still come from the unscoped task-cycle query, so the CSV can disagree with its own export-only fields. Overwritten criteria are counted from existing `director.scores` joined to selected-use-case scorecards, with `ai_scored`, changed value, and an identifier set drawn from all template revisions (`retrieve_manual_qa_stats.go:1455-1545`). This is a count, not a per-criterion score breakdown; under the agreed no-row-for-inapplicable rule it need not apply the latest criterion scope. Historical score rows should remain included according to their scorecard's pinned revision.
5. `RetrieveManualQAStats` validates one **template**, not one use case (`:845-859`); its group-by dispatch has time, analyst, and agent patterns but no use-case dimension (`:109-194`). `RetrieveQMTaskStats` supports only time and task+time (`retrieve_qm_task_stats.go:249-270`). A per-use-case drilldown cannot be obtained from the present response shape. Add grouping/result support or issue separate scoped requests for a small selected set, then combine the same selected set for the roll-up. Preserve the task × cycle overall row.
6. The current Evaluations tab has no per-criterion score table. It needs scorecard-use-case filtering for its present counts/averages and score-row filtering for overwritten criteria, both possible in PostgreSQL. If a future view needs per-criterion values, join `director.scores` to `director.scorecards`, filter the scorecard's concrete use case, and group by `scorecards.usecase_id` and `scores.criterion_identifier`. The schema stores `scorecards.usecase_id`, `template_revision`, and score rows (`apiserver/sql-schema/director/director-schema.sql:150-245`); do not filter historical scores by today's template JSON. The schema has scorecard submit-time and scorecard/criterion indexes (`:458-475`), but query cost remains unmeasured.

The minimal existing-query change is a `scorecards.usecase_id IN (<selected IDs>)` predicate in the two missing scorecard branches, before `GROUP BY` or Go aggregation. An exploratory per-criterion breakdown would use the shape `FROM director.scores s JOIN director.scorecards sc ON (customer, profile, scorecard_id)`, constrain `sc` by customer/profile, submitted interval, template/task and selected `sc.usecase_id`, then group by `sc.usecase_id, s.criterion_identifier`. Actual score-row existence encodes applicability for evaluated scorecards; any report of *unscored applicable* criteria would additionally need the pinned template revision and is outside this tab's current queries.

## Plan implication and verification gate

The earlier plan statement that QM Report stats already filter scorecards by use case **throughout** was too broad. The draft should explicitly require both missing predicates, shared-task discovery/period fixes, common frontend filter state, and a separate use-case breakdown contract. Completion-rate denominator for a selected subset of a shared task is still a product/aggregation decision; task-wide quota divided by filtered scorecards would be misleading. Once the task representation and breakdown query shape are chosen, run PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` or equivalent read-only representative comparisons for one vs multiple selected use cases and shared-task data. No live performance claim follows from this source review.
